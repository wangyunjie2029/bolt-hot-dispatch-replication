# 基于 LLVM BOLT 的热分派链复制优化（Hot Dispatch Replication）

> 大规模数据处理系统 · 课程项目（一）
> 王赟杰　51295903090　2026-12

## 摘要

本文在 LLVM 主线 BOLT（commit `88658a47`，2026-11-18）上设计并实现了一个新的代码布局优化：
**热分派链复制（Hot Dispatch Replication，HDR）**。

机器码布局有一个结构性约束：**一个基本块在一次布局中只能从唯一一个前驱顺序落入
（fall-through）**，其余前驱必须保留一条 taken 分支。解释器、虚拟机、查询引擎的分派点恰恰是
典型的高扇入块：每个 case 体都以 `jmp dispatch` 收尾。BOLT 现有的 `ext-tsp` 只重排块顺序，
最多让一个 case 顺序落入分派块；主线的 `-tail-duplication` 默认关闭、上限 24 字节，且只处理
单后继"尾块"，不覆盖这种高扇入分派场景。

HDR 依据 profile 选出"小而热"的分派链（取指/越界检查 + 间接跳转），把整条链复制到最热的前驱
之后，把 `jmp dispatch` 变成顺序落入。优化默认关闭，由 `-replicate-hot-dispatch` 控制，并带有
扇入、边计数、链长度、副本数、字节预算等阈值。

实验表明：在分派密集的字节码 VM 上，HDR 在 BOLT 基础上再提速 **2.0%**（相对原始二进制
**17.9%**）；在 SQLite VDBE 主导的扫描负载上约 **1%**；在不含分派结构的直线型内核上
**不触发、无回退**。收益的量级与理论一致——一条被正确预测的 taken jmp 在现代 x86 上只需
不到一个周期，因此 HDR 的价值集中在"每条被解释指令都要分派一次"的场景。

## 1. 问题描述

### 1.1 为什么 taken 分支值得消除

前端取指每次遇到 taken 分支都要重新定向：消耗 BTB 表项、打断取指流水；而 fall-through 不需要
任何跳转指令。BOLT 的 `ext-tsp` 正是以"最大化 fall-through 边的权重"为目标来重排基本块。

### 1.2 结构性限制：一个块只能有一个 fall-through 前驱

```
   case_0 ──jmp──┐
   case_1 ──jmp──┤        ┌─────────────────────────┐
     ...   ──jmp──┼───────▶│ dispatch: cmp; ja; jmp *jt│
   case_N ──jmp──┘        └─────────────────────────┘
```

设分派块扇入为 N、执行 C 次，则任何布局下都有 (N−1)/N 的边是 taken 的：**平均每次分派要执行
接近一条 taken 直接跳转**。对解释器而言，这意味着每条被解释的指令都多付一次取指重定向。

### 1.3 BOLT 主线为什么没有解决

| 现有机制 | 行为 | 不足 |
| --- | --- | --- |
| `-reorder-blocks=ext-tsp` | 重排块顺序 | 不复制代码，受 1.2 限制 |
| `-tail-duplication` | 复制单后继尾块 | 默认 `none`；上限 24B；不针对高扇入分派 |
| `-split-functions` | 冷块拆到 `.text.cold` | 不改变热路径 taken 分支数 |
| `-indirect-call-promotion` | 间接调用去虚化 | 针对调用，不针对跳转表分派 |

## 2. 优化设计

### 2.1 核心变换

对分派链 `Head -> ... -> Tail`（Tail 以跳转表间接跳转结尾，链上每块单后继），把它整体复制到
热前驱 P 之后，并把边 P→Head 重定向到 P→Head′：

```
复制前：  P: ... ; jmp Head        Head: ... ; jmp *jt(,%rax,8)
复制后：  P: ... ; (fall through)  Head′: ... ; jmp *jt(,%rax,8)   ...   Head: ...
```

**为什么复制"链"而不是单块**：真实分派点通常不是单独一条间接跳转，而是"取指 → 越界检查 →
间接跳转"两三个块（编译器会把跳转表基址提到循环外）。只复制最后一块会丢掉取指与检查，语义
错误；复制整条链才成立。

### 2.2 候选判定

- Tail：以**带跳转表注解的间接跳转**结尾，不含 call，非 landing pad；
- 链：从 Tail 向上回溯，前驱满足"单前驱、后继数 ≤ 2、边指向当前块、同 fragment"，最多 8 块；
- Head：扇入 ≥ `-replicate-hot-dispatch-min-fanin`（默认 8），执行次数 ≥
  `-replicate-hot-dispatch-min-exec-count`（默认 100000）；
- 链总字节数 ≤ `-replicate-hot-dispatch-max-chain-bytes`（默认 48）。

### 2.3 前驱筛选与排序

P 必须是 Head 的**无条件跳转**前驱（`succ_size()==1`）、非 cold、非 landing pad、同 fragment，
且边计数 ≥ `-replicate-hot-dispatch-min-edge-count`（默认 10000）。候选按边计数降序，优先复制
最热的边；已经是布局相邻（天然 fall-through）的跳过。

### 2.4 预算

- `-replicate-hot-dispatch-max-copies`（默认 8）：每函数最多副本数；
- `-replicate-hot-dispatch-max-bytes`（默认 512）：每函数最多新增字节。

### 2.5 适用性判断（先验）

- **有效**：分派链短、扇入大、分派频率高——字节码解释器、表达式求值器、VDBE。
- **无效**：向量化/直线型代码、分派仅占很小比例的通用查询；复制只增加代码体积。

## 3. 实现

### 3.1 流水线位置

新 pass `ReplicateHotDispatch` 注册在 `ReorderBasicBlocks` **之后**、`EliminateUnreachableBlocks`
之前。位置是设计的一部分：重排已完成，副本插入后可直接紧随前驱，不必依赖 ext-tsp 再排一轮。

### 3.2 关键 API

- `BinaryFunction::createBasicBlock()` + `addInstructions()`：创建副本，跳转表注解随指令复制，
  副本与原块**共享同一张跳转表**（不新建表）；
- `BinaryFunction::insertBasicBlocks(Pred, ...)`：把副本按链序插到前驱之后，同步更新布局、
  CFI 与 landing pad；
- `removeSuccessor()` / `addSuccessor()`：把 P→Head 改为 P→Head′，并把链内边重定向到副本；
- 分支指令不手工改写，后续 `FixupBranches` 依据 CFG 重新生成，相邻即 fall-through。

### 3.3 正确性

1. 只复制"以跳转表间接跳转结尾、不含 call、非 landing pad"的块；
2. 副本后继与边计数从原块复制，链内边计数保持一致；
3. 原链各块执行计数减去迁移走的份额；
4. 选项默认 `false`，关闭时 pass 立即返回，二进制与主线完全一致；
5. 无 profile、非 simple、无跳转表的函数一律不动。

### 3.4 统计输出

```
BOLT-INFO: replicate-hot-dispatch: replicated 16 blocks in 1 functions,
added 192 bytes, removed 12285610 dynamically executed taken branches
```

## 4. 实验

### 4.1 环境

Ubuntu 24.04 容器（Docker Desktop / WSL2），16 vCPU / 8 GiB；clang 18.1；BOLT 自建
Release 版（X86-only，LLVM 24.0.0git）。

工作负载统一用 `-O2 -g -Wl,-q -fno-pie -no-pie -fcf-protection=none` 编译：

- `-Wl,-q`：保留重定位，BOLT 才能改写；
- `-fno-pie -no-pie`：把 PIC 跳转表变成绝对地址表。**实测发现**：PIE 下编译器会把跳转表基址
  提到循环外，BOLT 的 `analyzeIndirectBranch` 无法回溯该基址，整个函数被判为非 simple 而拒绝
  优化——这是 BOLT 对 GCC/clang PIE 分派循环的一个已知盲区，也是本实验必须关掉 PIE 的原因；
- `-fcf-protection=none`：避免 `notrack` 前缀干扰间接跳转识别。

profile 用 BOLT instrumentation（`-instrument` → 运行 → `.fdata`），是精确块/边计数，不是采样。

### 4.2 负载与对照

| 负载 | 说明 | 作用 |
| --- | --- | --- |
| `vm_dispatch` | 自建寄存器字节码 VM，26 条指令循环，switch 分派 | 分派密集，预期受益 |
| SQLite 3.54 | 30 万行表，6 条扫描+表达式查询 ×8 遍 | 真实 DB，VDBE 分派 |
| `flat_kernel` | 4 路展开的浮点内核，无 switch | 对照：不应触发、不应回退 |

对照：`orig`（原始）/ `bolt`（默认流水线：ext-tsp + hfsort + split-functions）/ `bolt+hdr`。

### 4.3 方法

`scripts/compare.py`：每轮把各变体**随机顺序**各跑一次，重复 15～21 轮，取中位数；预热 2 轮。
这样机器的缓慢漂移对所有变体影响相同。

### 4.4 结果

**vm_dispatch（n=15）**

| 版本 | 中位耗时 | 相对 orig |
| --- | --- | --- |
| orig | 0.5475 s | 1.000× |
| bolt | 0.4741 s | 1.155× |
| **bolt+hdr** | **0.4646 s** | **1.179×** |

HDR 相对 BOLT 再快 **2.0%**；BOLT 日志显示复制 8 块 / +100 B / 消除 88.5 万次动态 taken 跳转。

**SQLite 扫描负载（n=15）**

| 版本 | 中位耗时 | 相对 orig |
| --- | --- | --- |
| orig | 2.0625 s | 1.000× |
| bolt | 1.9595 s | 1.053× |
| bolt+hdr（8 副本） | 1.9632 s | 1.051× |
| **bolt+hdr（40 副本）** | **1.9375 s** | **1.065×** |

VDBE 分派链扇入 **111**，复制 8 条链时消除 1228 万次、40 条链时 1468 万次动态 taken 跳转。
默认 8 副本的收益与 BOLT 持平（在噪声内），放大到 40 副本后相对 BOLT 约 **+1.1%**。通用查询
混合负载（含连接、排序、窗口函数，results/sql_final.json）上收益被摊薄到 +0.3%（8 副本），
40 副本时为 −0.8%——分派只占执行时间一小部分时，复制带来的代码膨胀开始盖过收益，这也印证了
第 5 节的适用性判断。

**flat_kernel（对照，n=13）**

| 版本 | 中位耗时 | 复制块数 |
| --- | --- | --- |
| orig | 0.0289 s | — |
| bolt | 0.0295 s | — |
| bolt+hdr | 0.0286 s | **0** |

pass 报 `replicated 0 blocks`，差异在 ±2% 噪声内，**没有回退**——满足"不满足优化条件的负载不得
退化"的要求。

### 4.5 结果分析

理论收益可以估算：SQLite 扫描负载每轮消除约 1200 万次 taken 跳转，按每次 0.5～1 周期计，
约 0.6～1.2 亿周期，占 2 秒（约 60 亿周期）的 1%～2%，与实测 1% 一致。VM 基准里分派占比更高
（每条 VM 指令一次分派），因此收益接近 2%。

结论：**HDR 的收益上界由"分派次数 × 单次 taken 分支成本"决定**，它不是一个"通用加速"手段，
而是针对分派循环的定向优化。

## 5. 局限性

1. **收益天花板低**：现代 CPU 对 taken 直接跳转预测极准，单次成本 <1 周期，因此只在分派密集
   的代码上有意义；通用数据库负载上通常 <1%。
2. **依赖 BOLT 能分析该函数**：PIE + 循环外提跳转表基址会让 BOLT 放弃整个函数（见 4.1），
   这类二进制上 HDR 无法生效；本实验通过 `-no-pie` 规避，但没有从根上修复 BOLT 的分析能力。
3. **代码体积增加**：每个副本 +链长度字节；预算参数控制不当会加剧 I-cache 压力。
4. **只处理无条件前驱**：条件分支进入分派块的场景未覆盖（此时 fall-through 已被占用的概率低，
   收益也低）。
5. **profile 敏感**：边计数偏差会复制并不热的边；本实验用 instrumentation 精确计数规避。

## 6. 复现

```bash
docker build -f docker/Dockerfile -t bolt-hdr .
docker run --rm -it -v $PWD/work:/work bolt-hdr
# 容器内：
bash /opt/scripts/run_all.sh /work
```

产物：`/work/*.json`（测量原始数据）、`/work/*_hdr.log`（BOLT 统计）、`patch/`（代码 patch）。
